# 第一部分：Git 版本管理

## 1.1 为什么运维要会 Git

| 场景 | 没有 Git | 有 Git |
|---|---|---|
| 脚本改坏了 | 凭记忆改回去（可能改错） | `git checkout` 一键回滚 |
| 想知道改了哪 | 翻聊天记录 | `git diff` 看差异 |
| 多人协作 | 互相发文件（版本混乱） | 分支 + 合并 |
| 服务器炸了 | 脚本全丢 | **GitHub 上还有一份** |

**你现在已经体会到的**：backup.sh 和 README 现在**同时存在于 sv01 和 GitHub**——服务器炸了也不怕。

## 1.2 三个区域（Git 最核心的心智模型）

```
工作区（你编辑的文件）
    │ git add
    ▼
暂存区（准备提交的内容）
    │ git commit
    ▼
仓库 .git（本地历史，永久保存）
    │ git push
    ▼
远程仓库 GitHub（异地副本）
```

**你今晚走的就是这条路**：`cp` 进目录（工作区）→ `git add .`（暂存）→ `git commit`（本地仓库）→ `git push`（GitHub）。

## 1.3 你的 commit 记录解读（git log --stat 的输出）

```
commit 1c3a570... (HEAD -> main, origin/main)
Author: Jasper <166681586+Jasperzzzch@users.noreply.github.com>
Date:   Fri Sep 4 00:16:13 2026 +0800

    sv01 delivery:hardening + nginx + backup automation

 backup.sh      |  8 ++++++++
 sv01-README.md | 39 +++++++++++++++++++++++++++++++++++
 2 files changed, 47 insertions(+)
```

| 字段 | 含义 |
|---|---|
| `1c3a570` | commit 的哈希 ID（唯一标识），回滚时用它 |
| `(HEAD -> main, origin/main)` | 本地 main、远程 main **完全同步**（这正是你第二次 commit 时"nothing to commit"的原因） |
| `Author: ... noreply.github.com` | 你的**隐私署名邮箱** |
| `+0800` | 时区（你昨天修好的 Asia/Shanghai 生效了） |
| 文件统计 | 两个文件、47 行新增 |

## 1.4 邮箱与身份（你今晚学到的真实工程实践）

**问题**：commit 邮箱会永久留在公开仓库里，任何人都能看到。

**你的解法（最优解）**：用 GitHub 的 **noreply 隐私邮箱**
```
166681586+Jasperzzzch@users.noreply.github.com
```

**为什么它是最优解**（三全其美）：

| 诉求 | 满足方式 |
|---|---|
| 提交要关联到我的 GitHub 账号 | ✅ noreply 地址唯一对应你的账号（GitHub 网页上显示你的头像就是证明） |
| 真实邮箱不能暴露 | ✅ 公开的只是 noreply 地址，收不到任何邮件 |
| 不能被 GitHub 的 Block 机制拦截 | ✅ 勾选了"Block command line pushes that expose my email"时，用真邮箱推送会被拒，noreply 不受影响 |

**结构解读**：`用户ID+用户名@users.noreply.github.com`——166681586 是你的 GitHub 数字 ID。

**注意**：它**不是收件邮箱**（发信到这儿你收不到），也不是登录邮箱（登录仍用 QQ 邮箱）。它只是 commit 里的匿名化署名标识。

## 1.5 SSH 密钥：每台机器一把钥匙（你今晚补上的关键认知）

**你踩的坑**：`git push` 时报 `Permission denied (publickey)`。

**根因**：
- 你的第一把密钥在 **Windows** 上（D2 生成）→ Windows → GitHub ✅
- 但 push 是在 **sv01（Linux）** 上执行 → sv01 没有自己的私钥 → 无法向 GitHub 证明身份 ❌

**解法**：在 sv01 上**新生成一对密钥**，把它的公钥**也**加到 GitHub。

**这是行业标准做法**：

| 机器 | 私钥位置 | 公钥是否已在 GitHub |
|---|---|---|
| Windows 笔记本 | `C:\Users\Jasper\.ssh\id_ed25519` | ✅ |
| sv01 服务器 | `~/.ssh/id_ed25519` | ✅ |

**为什么一台机器一把钥匙**：
1. **丢了哪台就删哪台的公钥**，其他机器不受影响
2. 不需要把私钥拷来拷去（**私钥传输 = 安全风险**）
3. 出问题时能精确定位是哪台机器在操作

# 第三部分：今晚踩的坑（每个都有价值）

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| **not a git repository** | commit/push 报这个 | 你在 `~` 下执行，仓库在 `~/linux-server-delivery` | `cd` 进仓库（**你第二次自己解决了，没问我** ✅） |
| **remote origin already exists** | add remote 报错 | 之前已添加过 | `git remote -v` 看 → 地址错就用 `set-url` 修 |
| **Permission denied (publickey)** | push 被拒 | sv01 没有 GitHub 认可的私钥 | sv01 生成新密钥 + 公钥加 GitHub |
| **跨机器路径无效** | 文件在主机上，PowerShell 在笔记本 | 三台机器的拓扑没理清 | 改走剪贴板 + heredoc 写入 |

**第 4 个坑是我的失误**（给你的路径依赖了错误的机器——你的操作机是笔记本，文件在主机上）。**但它暴露了一个真实的运维常识**：跨机器操作时，先想清楚"文件在哪、命令在哪执行"。

# 第四部分：面试考点

| 问题 | 答 |
|---|---|
| Git 三个区域 | 工作区 → 暂存区(add) → 本地仓库(commit) → 远程(push) |
| 怎么回滚 | `git checkout 文件`（未提交）/ `git reset --hard commitID`（已提交，危险） |
| commit 邮箱有什么讲究 | 用 GitHub noreply 邮箱：关联账号 + 不暴露真实邮箱 + 不被 Block 拦截 |
| 多台机器怎么用 Git | 每台机器一把 SSH 密钥，公钥都加到 GitHub，私钥不出本机 |
| 运维为什么要写文档 | 可交接、可复现、可审计；没文档的服务器没人敢接手 |
| 交付文档写什么 | 服务器信息 / 交付清单 / 常用操作 / 备份恢复 / 排障记录 / 已知事项 |
