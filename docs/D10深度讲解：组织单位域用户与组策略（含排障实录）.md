## 二、概念地基（人话版）

### 2.1 OU 是什么？为什么非要建一个？

OU（Organizational Unit，组织单位）= AD 里的"部门文件夹"。它同时是三样东西：

1. **整理工具**：把用户、计算机按部门归堆（ops OU 里住张三）；
2. **GPO 唯一能挂的钩子**：组策略只能链接到站点/域/OU——**注意：内置的 Users 和 Computers 是"容器"不是 OU，不能链接 GPO**。这就是"为什么不直接用自带容器、非要新建 OU"的标准答案；
3. **委派的边界**：生产中可以把某个 OU 的管理权下放给某个人（本次实验未涉及，知道有这功能即可）。

### 2.2 域用户的命名与初始密码

- 命名 `zhang.san`（姓.名拼音）是企业通行规范，登录名、邮箱名天然一致。
- 建号时勾选「用户下次登录时须更改密码」：初始密码只有管理员和本人知道过一次，第一次登录强制换成只有本人知道的——对应真实企业"HR 开户给初始密码，员工首登自改"的流程。
- 改密受**域密码策略**约束（复杂度：大小写+数字+符号至少三类；Qwer5678! 合规）。

### 2.3 GPO 的两个配置面：跟人走 vs 跟机器走（本 D 最核心概念）

| 配置面 | 跟谁走 | 例子 | 应该挂哪 |
|---|---|---|---|
| **用户配置** | 跟**用户对象**走——用户登录到任何机器都生效 | 隐藏桌面图标（ops-policy） | 放用户的 OU（ops） |
| **计算机配置** | 跟**计算机对象**走——只对这台机器生效 | "允许本地登录"名单 | 放机器的 OU（Domain Controllers） |

张三的桌面图标策略挂在 ops OU（张三的家），不管他登录哪台电脑都跟着他；
"DC01 允许谁登录"是 DC01 这台机器的设置，必须挂在 DC01 所在的 Domain Controllers OU。
**挂错位置 = 策略永远不生效**——这是今天排障的第一个思维关口。

### 2.4 GPO 生效四环（今天用血泪验证的模型）

```
① 配置 → ② 链接 → ③ 刷新 → ④ 落地
```

| 环节 | 含义 | 验证工具/方法 |
|---|---|---|
| ① 配置 | GPO 里的设置写对了 | 编辑器里重新打开设置看名单 |
| ② 链接 | GPO 挂在了对象所在的 OU，且链接已启用 | GPMC 里点 OU → 右侧「已链接的组策略对象」标签 |
| ③ 刷新 | 客户端把策略拉下来了（自动 ≤90 分钟，`gpupdate /force` 立即刷） | `gpresult /r` 看"已应用的组策略对象"列表 |
| ④ 落地 | 策略内容真正合并进系统生效值 | `secedit /export` 导出本地有效安全策略 |

**工具分工（重要结论）**：`gpresult` 只能证明"GPO 应用到了这台机器"，**不能**证明"里面的权限真正合进了系统"——后者要用 `secedit /export` 看最终生效值。今天正是靠这一刀切开了谜团。

## 四、排障实录（17:49 - 18:43，全程真实数据）

### 4.1 症状与第一层推理：先分清"认证失败"还是"授权失败"

关键观察：**改密码成功了，登录才失败**。
- 改密码走 Kerberos 密码修改协议（kpasswd，464 端口），**不检查登录权限**——它成功，说明账号存在、旧密码正确、认证链路全通；
- 登录才检查"允许本地登录"权限——它失败，说明卡的是**授权**，不是账号。

> 排障心法：Windows 登录类报错故意写得很含糊（防攻击者探测），运维要做的第一刀就是把它切成"认证问题"（账号/密码/锁定/禁用）还是"授权问题"（登录权限/限制）。本例一步切对，方向就没跑偏。

**第一判断**：域控默认不给普通域用户本地登录权限。
依据（后来被 secedit 证实）：DC 出厂时「允许本地登录」名单只有运营组（详见 4.5 的实测名单），Domain Users 不在其中。DC 是"户口本保管处"，不是给人办公的工作站——这是微软有意的安全设计。

### 4.2 修复尝试：新建 dc-logon-rights 并挂到 Domain Controllers OU

思路：不动默认策略，新建一条 GPO 给名单加人。路径：
gpmc.msc → Domain Controllers OU → 右键「在这个域中创建 GPO 并在此处链接」→ 命名 dc-logon-rights → 编辑 → 计算机配置 → 策略 → Windows 设置 → 安全设置 → 本地策略 → 用户权限分配 → 「允许本地登录」→ 添加 Domain Users。

**踩坑 ①：加了 Domain Users 后弹出黄色警告「管理员必须被授予登陆本地权限」**
- 本质：安全提醒，不是报错。触发条件 = 当前定义的名单里没有 Administrators。
- 处置：把 `SJZLAB\Administrators` 也加进名单（运维铁律：改登录权限永远给管理员留后门），警告随之消失，变成常规"兼容性"说明。

**踩坑 ②：点应用/确定"没反应"，关窗重开后名单消失**
- 先澄清：这个对话框保存时**本来就安静**——应用键没有任何提示，按钮变灰 = 已保存。判断成功与否的唯一标准是"重开后还在不在"。
- 处置：全部关窗 → `gpmc.msc` 全新打开 → 重新配置 → 当场重开验证。18:16 完成保存（GPO 修改时间 2026/9/4 18:16:28 为证）。

### 4.3 验证链逐环排查：配置 ✓ → 链接 ✓ → 刷新 ✓ → 但还是被拒？！

- **配置 ✓**：重开「允许本地登录」可见 `Administrators + SJZLAB\Domain Users`，「应用」按钮灰色（无未保存更改）。
- **链接 ✓**：GPMC 中 Domain Controllers OU 的「已链接的组策略对象」标签显示：链接顺序 1 = Default Domain Controllers Policy，链接顺序 2 = dc-logon-rights，均已启用链接。
- **刷新 ✓**：DC01 管理员 PowerShell 执行：

```
gpupdate /force
```
预期输出（实测）：
```
正在更新策略...

计算机策略更新成功完成。
用户策略更新成功完成。
```

```
gpresult /r
```
关键摘录（实测）：
```
计算机设置
-----------
CN=DC01,OU=Domain Controllers,DC=sjzlab,DC=local
上一次应用组策略的时间: 于 2026/9/4，18:25:26
已应用的组策略对象
-------------------
Default Domain Controllers Policy
dc-logon-rights
Default Domain Policy
```
dc-logon-rights 白纸黑字在"已应用"列表里。**策略应用了，用户却还是登不上**——矛盾升级。

### 4.4 secedit 实锤：看到"最终生效值"的那一刻

```
secedit /export /cfg C:\secpol.txt
Select-String -Path C:\secpol.txt -Pattern "SeInteractiveLogonRight"
```

**修复前实测输出**：
```
C:\secpol.txt:110:SeInteractiveLogonRight = *S-1-5-32-544,*S-1-5-32-548,*S-1-5-32-549,*S-1-5-32-550,*S-1-5-32-551,*S-1-5-9
```

SID 对照（背下来，面试能直接画）：

| SID | 是谁 |
|---|---|
| S-1-5-32-544 | BUILTIN\Administrators |
| S-1-5-32-548 | BUILTIN\Account Operators |
| S-1-5-32-549 | BUILTIN\Server Operators |
| S-1-5-32-550 | BUILTIN\Print Operators |
| S-1-5-32-551 | BUILTIN\Backup Operators |
| S-1-5-9 | NT AUTHORITY\Enterprise Domain Controllers |
| S-1-5-21-<域RID>-513 | **Domain Users ← 名单里没有它！** |

**结论**：实际生效名单 = 默认域控策略的原始名单，dc-logon-rights 里的授权**没有被合并进生效值**。同 OU 上两条 GPO 定义同一权限时，落地的是优先级更高的那条（默认域控策略，链接顺序 1）——新建 GPO 的定义被覆盖了。

> **诚实修正**：此前"多条 GPO 的允许权限是并集"的判断被本次实测推翻。教训值得写进任何运维手册：**文档说法与实测不一致时，信实测；用户权限的最终裁判是 secedit /export，不是 gpresult。**

### 4.5 最终修复：把授权直接写进"赢家"策略

既然生效的是默认域控策略，就把 Domain Users 加进它（最短路径；生产环境的规范做法见第六节追问预案）：

1. gpmc.msc → 右键 **Default Domain Controllers Policy** → 编辑；
2. 计算机配置 → 策略 → Windows 设置 → 安全设置 → 本地策略 → 用户权限分配 → 「允许本地登录」；
3. 添加 `SJZLAB\Domain Users` → 确定 → 关编辑器；
4. `gpupdate /force`；
5. secedit 复查（先重跑 `secedit /export /cfg C:\secpol.txt`，再 Select-String）——**修复后实测输出**：
```
C:\secpol.txt:113:SeInteractiveLogonRight = Domain Users,*S-1-5-32-544,*S-1-5-32-548,*S-1-5-32-549,*S-1-5-32-550,*S-1-5-32-551,*S-1-5-9
```
（Domain Users 以名字形式出现在名单里，与 SID 形式等价，secedit 会自动解析。）
6. 注销 → zhang.san + 新密码 → **登录成功，桌面全空（ops-policy 生效）→ 18:43 收官。**

## 五、知识结晶（今天的五颗钉子）

1. **先切认证还是授权**：改密码能成功 = 认证链路通；登录失败 = 授权问题。一刀切对，全盘不歪。
2. **GPO 生效四环**：配置 → 链接 → 刷新 → 落地。前三环用"看截图/链接标签/gpresult"验证，第四环**必须 secedit**。
3. **gpresult 与 secedit 的分工**：gpresult 管"策略有没有应用"，secedit 管"权限有没有真正生效"。工具不能互相替代。
4. **拒绝覆盖允许**：Deny 是一票否决（本次虽未撞上，但排查时是头号嫌疑之一——生产中"拒绝本地登录"是最容易锁死全场的操作）。
5. **实测 > 文档**：secedit 输出与预期模型不符时，改认知、留证据、再总结——这就是运维的"科学方法"。

## 六、面试话术与追问预案

### 6.1 两分钟故事（可直接背诵）

> "我在验证组策略时踩过一个很深的坑：域用户首次登录，改密码成功，但登录报'不允许使用你正在尝试的登录方式'。我先切分认证和授权——改密码走 Kerberos 的密码修改协议，不检查登录权限，它能成功说明账号密码都没问题，卡的是登录权限。然后我沿 GPO 生效四环查：配置对、链接对，gpresult 显示策略已经应用，但用户还是登不上。最后用 secedit /export 导出本地生效安全策略，发现'允许本地登录'名单里根本没有 Domain Users——原来同一 OU 上两条 GPO 定义同一权限时，实际生效的是优先级高的默认域控策略，我新建的 GPO 被覆盖了。把授权直接加进生效中的策略，secedit 复查名单里出现 Domain Users，登录恢复，同时用户策略（隐藏桌面图标）也正常生效。这个案例让我记住三件事：登录报错先切认证还是授权；gpresult 只证明应用了，secedit 才是用户权限的最终裁判；文档和实测不一致时，信实测、留证据。"

### 6.2 追问预案（8 条）

| 追问 | 答案要点 |
|---|---|
| 为什么域控默认不让普通用户登录？ | DC 是基础设施不是工作站，默认名单只给运营组，缩小攻击面；普通用户登录客户端/成员服务器 |
| 错误提示为什么这么含糊？ | 防探测的安全设计；真实原因看安全日志 4625（登录类型 2=交互、3=网络、10=远程桌面，状态码区分原因） |
| 为什么不把张三加进 Administrators？ | 最小权限原则：给登录权不给管理权；加组是"授权扩大"，加登录权是"通道放行" |
| 生产环境怎么规范做？ | 不动默认策略；新建 GPO 且确保优先级覆盖默认（链接顺序上移）；用专用运维组而非 Domain Users；变更带文档和回滚预案 |
| GPO 优先级顺序？ | LSDOU：本地→站点→域→OU，后者覆盖前者；同 OU 内链接顺序号小者优先；"强制"防中间被拦截 |
| dc-logon-rights 后续怎么处理？ | 实验室：可留（无害但注明不生效）或删除；生产：应删或调整优先级后重写，避免"看起来配了其实没生效"的假策略 |
| gpupdate 与 gpresult 区别？ | 一个刷新（/force 立即同步刷），一个查应用结果（/r 快速、/h 出 HTML 报告） |
| 如果当时有"拒绝本地登录"配了 Domain Users 会怎样？ | Deny 一票否决所有 Allow——这也是本次排查的头号嫌疑之一，最终靠 secedit 名单排除了它 |
