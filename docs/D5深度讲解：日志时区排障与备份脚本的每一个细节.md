# D5 深度讲解：日志、时区排障与备份脚本的每一个细节

> 配套：行动指南 D5（日志 + 备份脚本）。本报告记录了 D5 里最有价值的部分——**你自主发现并修复了一个"没有报错的问题"（时区），并写出了第一个运维脚本**。

---

## 开篇：D5 在干两件什么事

一句话：**给服务器装上"黑匣子"（日志体系）和"保险柜"（备份脚本）。**

- 日志回答的问题是：**"过去发生了什么？"**——排障的起点，审计的依据
- 备份回答的问题是：**"坏了怎么恢复？"**——运维的最后一道防线

这两样是运维的日常底座：**80% 的故障排查从看日志开始，100% 的数据安全靠备份兜底。**

# 第一部分：日志体系（服务器的黑匣子）

## 1.1 两套日志系统（你要分清它们在哪）

| | journald（systemd 日志） | 传统文本日志 |
|---|---|---|
| 位置 | 二进制，内存+磁盘，`journalctl` 查看 | `/var/log/` 下的文本文件 |
| 范围 | **所有服务**统一收集（systemd 管的） | 每个应用自己写自己的 |
| 存储 | **内部存 UTC**，显示按时区换算 | **写死当时的时间字符串** |
| 改时区后 | **历史日志自动修正** ✅ | 旧条目不变，**时间线裂缝** ⚠️ |
| 查看 | `journalctl -u 服务 --since today` | `tail -f /var/log/xxx.log` |

## 1.2 journalctl 三板斧（排障起点）

```bash
journalctl -u nginx --since today    # 看某个服务的日志（-u 按服务过滤）
sudo journalctl -xe                  # 看最近的系统日志（-x 带解释 -e 到末尾）
sudo tail -f /var/log/nginx/access.log   # 实时跟踪文本日志（Ctrl+C 退出）
```

**运维铁律：服务器出问题时，第一反应就是 `journalctl -xe`。** 这条命令相当于"到案发现场看监控"。

## 1.3 你的日志时间线还原（journalctl -xe 的输出讲了一个故事）

你跑 `-xe` 时看到的日志，其实是**你自己 19:16-19:19 的操作记录**：

| 时间 | 日志内容 | 发生了什么 |
|---|---|---|
| 19:16:19 | `Started session-76.scope - Session 76 of User jasper` | 你重新 SSH 登录（第 76 号会话） |
| 19:16:34 | `Starting systemd-timedated.service` | 你执行 `timedatectl` → 系统按需启动时间服务 |
| 19:17:01 | `CRON... (root) CMD (run-parts /etc/cron.hourly)` | 整点例行任务（cron 在干活） |
| 19:17:04 | `systemd-timedated.service: Deactivated` | 时间服务**用完自动停止** |
| 19:19:54 | `sudo[34372]: jasper : TTY=pts/0 ; PWD=/home/jasper ; COMMAND=journalctl -xe` | **你自己敲的命令被完整记录** |

### ⭐ sudo 审计日志（D3"可追溯性"的活证据）

```
jasper : TTY=pts/0 ; PWD=/home/jasper ; USER=root ; COMMAND=/usr/bin/journalctl -xe
```

| 字段 | 含义 |
|---|---|
| `jasper` | 谁 |
| `TTY=pts/0` | 从哪个终端（pts/0 = SSH 会话） |
| `PWD=/home/jasper` | 在哪个目录 |
| `USER=root` | 切换成了谁 |
| `COMMAND=...` | 执行了什么（精确到路径） |

**这就是 D3 说的"加 sudo 组而非给 root 密码，因为可追溯"——追溯记录长这样。** 企业安全部门查事故，翻的就是 `/var/log/auth.log` 里的这些。

查自己全部 sudo 记录：
```bash
sudo grep sudo /var/log/auth.log
```

## 1.4 按需启动（systemd 的智能）

`timedated` 服务 19:16:34 启动、19:17:04 自动停止——你没有任何手动操作。

**机制**：你敲 `timedatectl` → 通过 dbus 总线请求时间服务 → systemd **按需拉起** → 没人用了**自动回收**。不常驻内存、用完即走。

**为什么先进**：老式 Linux 的服务要么常驻（浪费），要么手动启停（麻烦）。systemd 的按需启动让系统更瘦、更安全（不跑的服务就没有攻击面）。

## 1.5 Nginx 访问日志解剖（combined 格式）

你的 access.log：

```
::1 - - [03/Sep/2026:09:54:59 +0000] "GET / HTTP/1.1" 200 24 "-" "curl/8.5.0"
192.168.207.1 - - [03/Sep/2026:09:56:09 +0000] "GET / HTTP/1.1" 200 54 "..." "Mozilla/5.0 ... Chrome/152..."
192.168.207.1 - - [03/Sep/2026:09:56:10 +0000] "GET /favicon.ico HTTP/1.1" 404 196 "http://192.168.207.128/" "..."
```

| 字段 | 含义 | 你的值说明了什么 |
|---|---|---|
| 客户端 IP | 谁在访问 | `::1`=自己（IPv6 localhost）；`192.168.207.1`=**你的宿主机** |
| 时间 [+时区] | 请求时刻 | 见第二部分（时区排障） |
| `"GET / HTTP/1.1"` | 请求方法 + 路径 + 协议 | GET 首页 |
| 状态码 | 200 成功 / 404 没找到 / 500 服务器错 | favicon 的 404 = Chrome 自动要图标，**正常现象不是故障** |
| 响应字节数 | 返回了多少 | **24 vs 54 的彩蛋**：curl 拿原始 24 字节；Chrome 要了 gzip 压缩版，24 字节的小文件压缩后**反而膨胀到 54**（压缩头开销） |
| Referer | 从哪个页面跳来 | favicon 的 referer 是首页（浏览器自动附带） |
| User-Agent | 客户端身份 | `curl/8.5.0` vs `Chrome/152`——服务器能识别访问者是谁 |

**运维用途**：通过 access.log 可以分析**谁在访问、访问什么、频率多少、有没有异常扫描**（比如大量 404 = 有人在扫你的目录）。

# 第二部分：时区排障（你今天最亮的表现）

**这是一次完整的排障案例，值得整段保留**——因为它是你**自主发现**的：没有报错、没有提示，你纯凭"09:53 和实际时间对不上"的直觉，揪出了一个真实隐患。

## 2.1 排障五段式（面试的标准叙事）

| 阶段 | 你做的 |
|---|---|
| **发现** | journalctl 显示 09:53，与实际时间 17:53 对不上，差 8 小时 |
| **定位** | `timedatectl` → `Time zone: Etc/UTC (UTC, +0000)`——装系统时选 English 一路默认，时区落在 UTC |
| **修复** | `sudo timedatectl set-timezone Asia/Shanghai`（立即生效，无需重启服务） |
| **验证** | `timedatectl` 显示 Asia/Shanghai (+0800)；Local time 19:10 CST；NTP active |
| **沉淀** | 时区应在**装机时就配置好**；上线后改时区会留下日志时间线裂缝 |

## 2.2 深层机制：UTC 是存储层，时区是显示层

改时区前后，journalctl 里同一条日志：

```
改前：Sep 03 09:53:06   ← 显示为 UTC
改后：Sep 03 17:53:06   ← 自动变成北京时间（+8h）
```

**底层存储的 UTC 一个字节没变**——journald 内部统一存 UTC，**显示时才按本地时区换算**。所以历史日志自动修正。

## 2.3 但文本日志会留下"时间线裂缝"

Nginx 的 access.log 是**应用自己写的时间字符串**：

```
[03/Sep/2026:09:54:59 +0000]   ← UTC 时代写的
[03/Sep/2026:09:56:09 +0000]   ← UTC 时代写的
[03/Sep/2026:19:29:33 +0800]   ← reload 之后写的（北京时间）⭐
[03/Sep/2026:19:31:49 +0800]   ← 北京时代
```

**新旧条目偏移量不同，共存于同一个文件**——排查历史问题时，把 +0000 的旧条目当北京时间看会差 8 小时。

## 2.4 Nginx 时区缓存（你撞上的第二个问题）

改时区后，你新 curl 的日志居然还是 `+0000`（`11:25:01 +0000`，实际是 19:25 CST）。

**根因**：Nginx 进程是 UTC 时代启动的，**时区被缓存在进程内存里**——改系统时区，常驻进程并不自动感知。

**修复**：`sudo systemctl reload nginx` → 之后的新日志变成 `19:29:33 +0800` ✅

**沉淀的方法论**：
> **改了系统级配置（时区/locale/内核参数），必须检查常驻服务是否需要 reload/restart。** "改完系统就完事"是新手思维，"改完系统再检查每个受影响的服务"是运维思维。

## 2.5 24 小时制（LC_TIME）

`date` 显示 `07:10:15 PM`（12 小时制）是因为 locale 是 **en_US.UTF-8**（美国习惯 AM/PM）。

**修复**：`sudo update-locale LC_TIME=C.UTF-8` + 重新登录 → `date` 输出 24 小时制。

**层级关系（容易混，记住这个表）**：

| 层 | 变量/配置 | 管什么 | 改了会影响历史数据吗 |
|---|---|---|---|
| **存储层** | 系统时钟（UTC） | 底层时间真相 | 永远不动 |
| 换算层 | 时区（timedatectl） | UTC ↔ 本地时间的换算 | journald 自动修正；文本日志出现裂缝 |
| 显示层 | LC_TIME（locale） | 数字显示成 12h 还是 24h | 纯显示，底层不动 |

## 2.6 为什么时区和时间准确是运维大事

- **排障靠时间线**：多台机器、多个应用的日志时间对不上，故障现场就无法还原
- **NTP 必须开着**：`System clock synchronized: yes` = 自动校时（你的是开的）；时间漂移会导致证书校验失败、定时任务错乱、分布式系统脑裂
- **企业规范**：所有服务器统一时区（要么全 UTC 要么全本地），**装机第一件事配时区**，上线后不再动

# 第三部分：logrotate（日志的保养计划）

## 3.1 为什么需要它

日志**每天增长、无限增长**——不管理的话，几个月后磁盘被日志撑爆，服务器宕机。logrotate 是系统的"日志管家"：**按周期切割 → 压缩旧文件 → 保留 N 份 → 删更旧的**。

## 3.2 你的 `/etc/logrotate.d/nginx` 逐行解读

| 配置 | 含义 |
|---|---|
| `/var/log/nginx/*.log` | 管理对象：nginx 目录下所有 .log |
| `daily` | 每天切一次 |
| `rotate 14` | 保留 **14 份**（两周历史），再旧自动删 |
| `compress` | 旧日志 gzip 压缩 |
| `delaycompress` | 最近一份**延迟一轮再压**（可能有进程还在写它） |
| `notifempty` | 空日志不切（不折腾） |
| `missingok` | 文件不存在不报错 |
| `create 0640 www-data adm` | 切割后新建空日志：权限 0640、属主 www-data（Nginx 的低权限 worker 身份）、属组 adm（运维组能读） |
| `postrotate` → `invoke-rc.d nginx rotate` | 切割后**通知 Nginx 重开日志文件**（USR1 信号） |

## 3.3 两个知识点呼应

**呼应 1（D3 权限）**：`create 0640 www-data adm`——日志归 www-data 写（服务身份）、adm 组读（运维身份）、其他人无权。**最小权限在日志上的落地。**

**呼应 2（inode）**：为什么切割完必须通知 Nginx 重开文件？

logrotate 的切割 = `mv access.log access.log.1`——**只改名字，inode 不变**。Nginx 进程还握着旧 inode 的句柄，会继续写旧文件；新建的空 access.log 反而没人写。所以必须让它**关闭旧句柄、打开新文件**。

**这和"删了大文件磁盘不释放"是同一个原理**：进程持有句柄。logrotate 的 postrotate 钩子就是为了打破持有。

## 3.4 手动强制切一次（看效果）

```bash
sudo logrotate -f /etc/logrotate.conf
ls -l /var/log/nginx/
```
会看到 `access.log.1`（被切走的）和一个全新的空 `access.log`（create 0640 新建的）。

# 第四部分：备份脚本（你的第一个运维脚本）

## 4.1 手册的两个隐藏坑（帮你修正过的）

| 手册写法 | 坑 | 修正 |
|---|---|---|
| 备份目录 `/home/ops/backups` | ops 家目录 **750**（D3 刚学的），jasper 写不进去 → Permission denied | 改为 `/home/jasper/backups` |
| 直接 `~/scripts/backup.sh` 运行 | `/etc` 里有 root 才能读的文件（如 shadow）→ tar 报错 + `set -e` 中断 | 用 **`sudo`** 运行 |

**这两个坑本身就是权限知识的应用**——你学 D3 的时候，绝对想不到它会在 D5 救你。

## 4.2 脚本逐行讲解（面试必被追问）

```bash
#!/bin/bash
```
shebang（释伴行）：告诉系统"用 bash 解释我这个文件"。没有它，系统不知道用什么跑。

```bash
set -euo pipefail
```
**防御性脚本的标准开头**（背下来）：
- `-e`：任何命令失败立即退出——**不会带病继续跑**（备份了一半的包比没有备份更危险）
- `-u`：使用未定义变量直接报错——防止变量名拼错后静默出错
- `-o pipefail`：管道中任何一环失败都算整体失败

```bash
BK=/home/jasper/backups
```
**必须写死绝对路径**——cron 和 sudo 环境下 `$HOME` 可能不是你以为的值（sudo 后变 /root）。依赖环境变量的脚本，在 cron 里就是定时炸弹。

```bash
mkdir -p $BK
```
`-p`：不存在则创建（含父目录）、已存在也不报错——幂等操作。

```bash
tar -czf $BK/etc_$(date +%Y%m%d).tar.gz /etc
```
- `-c` 创建包、`-z` gzip 压缩、`-f` 指定文件名
- `$(date +%Y%m%d)` = **命令替换**，运行时展开成今天日期（如 20260903）——每天一个新文件，不覆盖旧的
- **为什么备份 /etc**：它是全系统配置的家（网络、用户、服务配置都在里面）——丢了系统配置，服务全部要重配

```bash
find $BK -name "*.tar.gz" -mtime +7 -delete
```
**轮转保留**：`-mtime +7` = 修改时间**超过 7 天**的，直接删。
- 磁盘不会无限涨（自动清理）
- 7 天够回溯一周内的问题
- **这是磁盘空间的"自动刹车"**

```bash
echo "backup done at $(date)" >> $BK/backup.log
```
**留痕**：每次执行追加一条时间记录。运维习惯：**做了什么必须留痕**，否则出问题无法复盘"上一次备份是什么时候"。

## 4.3 tar 的安全提示（你问的那条）

```
tar: Removing leading `/' from member names
```

打包时用了绝对路径 `/etc`，tar **自动剥掉开头的 `/`**（存成 `etc/...`）并提示。

**为什么**：如果包里存绝对路径，解压时会**直接覆盖系统根目录下的同名文件**（包里有 /etc/passwd，解压 = 覆盖系统的 passwd）。剥掉 `/` 后解压是相对目录的，安全。

**面试点**："tar 打包绝对路径会怎样？"——答这个剥 `/` 机制 + 防覆盖目的。

## 4.4 一个验证习惯的价值

你粘贴 heredoc 时，**终端回显中间错乱了一行**（`=/home/j> set -euo...`），看起来吓人——但你跑了第 9 条 `cat ~/scripts/backup.sh`，**文件内容完全正确**。

**终端回显错乱 ≠ 文件内容错误**。多行粘贴时回显经常乱（尤其 SSH + Windows 终端），**验证要用 `cat` 读真实文件**，不要相信屏幕回显。

## 4.5 验收三连解读

```
-rw-r--r-- 1 root root   44 Sep  3 19:40 backup.log
-rw-r--r-- 1 root root 577K Sep  3 19:40 etc_20260903.tar.gz
```
- 属主 **root:root**：因为 sudo 跑的（root 的身份建的文件）——D3 权限知识的实战印证
- 权限 **644**：jasper 照样能读（root 建的文件默认 644，umask 022）
- 时间 **19:40:18 CST**：时区 + locale 修复的直接兑现

```
backup done at Thu Sep  3 19:40:18 CST 2026
```
留痕成功——以后每天 cron 跑一次，这个文件就多一行。

```
etc/  etc/default/  etc/default/amd64-microcode  ...
```
`tar -tzf` 列出包内容——**全是 `etc/` 开头的相对路径**（呼应 tar 安全特性）。

**"备份没验证 = 没有备份"**：一个从没解压过的备份包，你不知道它是好的还是坏的。真出事时打开发现是坏的，就是灾难。**验证一次 = 给备份上保险。**

# 第五部分：现实图景（企业里日志与备份怎么管）

## 日志管理

| 层级 | 做法 |
|---|---|
| 单机 | journald + logrotate（你现在做的） |
| 集中采集 | Filebeat/Fluentbit 收集 → ELK/Loki 集中存储检索（**模块 H 的话术已备**） |
| 审计 | auth.log 留存 ≥6 个月（等保要求）、堡垒机命令审计 |
| 监控联动 | 日志里出现 ERROR/OOM 关键词触发告警 |

## 备份管理

| 原则 | 内容 |
|---|---|
| **3-2-1 原则** | 3 份数据、2 种介质、1 份异地 |
| **备份验证** | 定期解压抽查（你今天做的） |
| **恢复演练** | 定期真的做一次"从备份恢复"（你的 mysqldump 恢复演练就是） |
| **RPO/RTO** | 能接受丢多少数据（RPO）、能接受停多久（RTO）——备份策略按这个设计 |

**你的脚本 vs 企业备份**：你备份的是 /etc（服务器配置），企业还会备份数据库（mysqldump，D19 做）、应用数据、并传到异地（OSS/NAS）。**原理完全相同，规模不同。**

# 第六部分：面试话术 + 追问预案

### 60 秒话术

> "日常运维我重点关注两件事：日志和备份。
>
> 日志方面，我用 journalctl 看系统级日志、tail -f 看应用实时日志，logrotate 管理切割轮转——比如 Nginx 的日志我配了每天切割、保留 14 份、自动压缩。中间踩过一个真实的坑：改完系统时区后发现 Nginx 日志还是 UTC 偏移，定位到是**进程启动时缓存了时区**，reload 之后新日志才用新时区——所以我的习惯是改完系统级配置，必须检查常驻服务是否需要重载，用服务实际生效的配置来验证，而不是只看文件。
>
> 备份方面，我写了一个 Shell 脚本：set -euo pipefail 严格模式开头，tar 打包 /etc 配置目录、文件名带日期、find 按修改时间清理 7 天前的旧包、每次执行留痕到日志。跑完我一定做验证——tar -tzf 确认包可用，因为备份没验证等于没有备份。这个脚本后面配了 cron 定时自动执行。"

### 追问预案

| 追问 | 答 |
|---|---|
| journalctl 和 /var/log 什么关系 | journald 是 systemd 的统一二进制日志（存 UTC、显示换算）；/var/log 是各应用自己写的文本日志；两者互补 |
| 为什么脚本开头 set -euo pipefail | 防御性编程：出错即停、防未定义变量、管道错误不吞——备份脚本带病运行比不运行更危险 |
| 备份保留 7 天怎么实现 | `find -mtime +7 -delete`，按修改时间清理，磁盘自动刹车 |
| tar 打包绝对路径会怎样 | GNU tar 剥离开头 / 并提示，防止解压覆盖系统文件 |
| 日志切割后为什么要 reopen | 进程持有旧 inode 句柄，mv 只改名字，不重开的话日志继续写进旧文件 |
| 什么时间做备份 | 业务低峰（凌晨），用 cron 定时；数据库备份还要考虑锁表/热备 |
| 3-2-1 原则 | 3 份数据、2 种介质、1 份异地 |
| 删了文件磁盘不释放 | 进程持有已删除文件句柄，`lsof | grep deleted`，重启进程或 `> 文件` 清空 |
