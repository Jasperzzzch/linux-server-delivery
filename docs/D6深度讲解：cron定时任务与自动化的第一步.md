# D6 深度讲解：cron 定时任务与自动化的第一步

> 配套：行动指南 D6（cron 定时任务）。全部解读基于你的真实输出。
> D6 的本质：**把"人记得做"升级成"系统自动做"**——这是运维自动化的第一块基石，也是你从"操作员"走向"工程师"的分水岭。

## 开篇：手动执行 vs 定时执行的差别

| | 手动（D5） | 自动（D6） |
|---|---|---|
| 谁执行 | 你记得、你敲 | 系统**永远准时**执行 |
| 你请假/忘了 | 备份就断了 | **照跑不误** |
| 凌晨 2 点 | 你不可能爬起来 | cron 毫无压力 |
| 累计价值 | 一次性动作 | **建立可靠的基础设施** |

**一句话**：运维的可靠性不靠人的记性，靠系统的机制。cron 就是第一个机制。

## 第一部分：cron 是什么

**cron 是系统的"闹钟管家"**——一个常驻后台的守护进程（daemon），每分钟醒一次，检查有没有到点该执行的任务，有就执行，没有就继续睡。

### 你的输出里的三个细节

```
no crontab for root - using an empty one
```
**root 从来没有建过定时任务**——cron 给 root 分配了一个空的 crontab 文件。每个用户的 crontab 是**相互独立**的（root 有 root 的，jasper 有 jasper 的）。

```
Select an editor.  1. /bin/nano  <---- easiest
```
第一次 `crontab -e` 让你选编辑器——你选了 nano（最容易），正确。

```
crontab: installing new crontab
```
保存退出后显示这个——**新任务已安装生效**（cron 每分钟会检查 crontab 文件的变更，自动加载，不需要重启任何东西）。

## 第二部分：五段格式详解

```
0  2  *  *  *   /home/jasper/scripts/backup.sh >> ... 2>&1
│  │  │  │  │
│  │  │  │  └─ 星期几（0-7，0 和 7 都是周日）
│  │  │  └──── 月份（1-12）
│  │  └─────── 日期（1-31）
│  └───────── 小时（0-23，24 小时制）
└──────────── 分钟（0-59）
```

### 常用写法速查

| 表达式 | 含义 |
|---|---|
| `0 2 * * *` | 每天凌晨 2:00（你的备份任务） |
| `*/5 * * * *` | 每 5 分钟 |
| `0 */2 * * *` | 每 2 小时整点 |
| `30 3 * * 1` | 每周一 03:30 |
| `0 0 1 * *` | 每月 1 号零点 |
| `0 9,18 * * 1-5` | 工作日的 9:00 和 18:00 |

**时区**：cron 跟随系统时区。你已改成 Asia/Shanghai，所以 `0 2` 就是**北京时间凌晨 2 点**——业务低峰，备份不影响任何使用。

## 第三部分：关键决策——为什么用 root 的 crontab

你执行的命令是 `sudo crontab -e`（不是 `crontab -e`），这是**有意为之**：

| 方案 | 结果 |
|---|---|
| ❌ jasper 的 crontab 里写 `sudo ~/scripts/backup.sh` | cron 环境里 **sudo 没法问你密码**（没有终端交互）→ 任务失败 |
| ✅ **root 的 crontab 里直接写脚本路径** | root 天然能读全 /etc，不需要提权 |

**判断标准**：脚本需要什么权限，就把 crontab 放在什么身份下。你的备份脚本要读 /etc 全部内容 → root 的 crontab。

**对比记忆**：
- `crontab -e` = 编辑**当前用户**（jasper）的定时任务
- `sudo crontab -e` = 编辑 **root** 的定时任务
- `sudo crontab -l` = 查看 root 的定时任务

## 第四部分：cron 环境的三个坑（你的脚本为什么全躲过了）

cron 执行任务时的环境和你登录时的环境**完全不同**，这是 cron 最著名的坑：

| 坑 | 登录会话 | cron 环境 | 你的脚本为什么没事 |
|---|---|---|---|
| **PATH 很短** | 完整 PATH | 只有 `/usr/bin:/bin` | tar、find、date 全在标准路径 ✅ |
| **HOME 不同** | 你的家目录 | 该任务所属用户的家目录（root 是 /root） | **BK 写死了绝对路径** `/home/jasper/backups` ✅（D5 埋的设计今天兑现） |
| **输出会丢** | 输出到屏幕 | 输出**发邮件**（没配邮件服务 = 丢失） | 你加了 `>> backup.log 2>&1` 重定向 ✅ |

**第三条的证明就在你的日志里**：backup.log 里连 `tar: Removing leading '/' ...` 这行 **stderr（错误输出）都被捕获了**——`2>&1` 在工作。

**面试点**："cron 任务不执行的常见原因"——答环境变量差异（PATH/HOME）、绝对路径问题、输出重定向，直接体现实战经验。

## 第五部分：输出重定向详解

```
0 2 * * * /home/jasper/scripts/backup.sh >> /home/jasper/backups/backup.log 2>&1
                                                          └────────┬────────┘
                                                            >> backup.log   2>&1
                                                            │                │
                                              追加标准输出(stdout)     把标准错误(stderr)
                                                                        也并入标准输出
```

| 片段 | 含义 |
|---|---|
| `>> 文件` | 标准输出**追加**到文件（不覆盖） |
| `2>&1` | 把 2（stderr 错误输出）重定向到 1（stdout）的位置——**错误也进同一个日志** |

**证据**：你的 backup.log 里有 `tar: Removing leading '/' ...` 这行——那是 tar 的**错误输出**，因为 `2>&1` 才被收集进日志。如果没写 `2>&1`，这行就丢了，将来排障会少关键线索。

## 第六部分：测试方法论（你今天做得最专业的一步）

你完美执行了"**先声明，后验证**"：

| 步骤 | 你做的 | 证明 |
|---|---|---|
| 1 | 写入正式任务 `0 2 * * *` | 任务已声明 |
| 2 | **临时改成 `21 23 * * *`**（3 分钟后） | 制造一个"马上就能验证"的场景 |
| 3 | `cat backup.log` → **23:21:01 出现新记录** | cron 真的会自动执行 ✅（秒级启动） |
| 4 | **改回 `0 2 * * *`** | 恢复正式配置 |

**为什么不直接信"写进去就会跑"**：因为 cron 任务失败时**默认没有任何提示**（输出发邮件，邮件没配就静默丢失）。**"写了"和"会跑"之间隔着环境差异、路径错误、权限问题**——只有实测才能确认。

**这是运维的核心素养**：你昨天在 SSH 上用的 `sshd -T` 验真、今天用临时时间实测 cron——**同一种思维：不是"我配了"，而是"我验证了它真的生效"。**

## 第七部分：现实图景（企业里的定时任务怎么管）

| 层级 | 做法 |
|---|---|
| 单机 | crontab（你现在做的） |
| 系统级 | `/etc/cron.hourly|daily|weekly`（你 journalctl 里见过它在跑） |
| 精确控制 | systemd timer（现代替代，支持依赖和错过补跑） |
| 集中管理 | 大厂用 Airflow/Rundeck 等调度平台，统一看任务成败 |
| 告警 | 任务失败发通知（你的脚本输出已重定向，配合 fail2ban 式监控可做告警） |

**cron 的弱点（面试加分）**：任务失败不会主动告警、错过执行点不会补跑（宕机跨过 2 点就丢了）——所以生产环境要么加失败告警，要么用 systemd timer（`Persistent=true` 支持补跑）。

## 第八部分：面试话术 + 追问预案

### 60 秒话术

> "我的备份脚本不是手动跑的，配了 cron 每天凌晨 2 点自动执行——放在 root 的 crontab 里，因为脚本要读全 /etc 必须用 root 身份；输出重定向到备份日志，标准输出和错误都收，方便追溯。上线前我做了实测：把执行时间临时改成 3 分钟后，确认 cron 真的触发了、日志真的新增了记录，才改回凌晨 2 点——不验证的定时任务等于没配。另外我写脚本时刻意用了绝对路径，因为 cron 的 PATH 和 HOME 与登录会话不同，这是 cron 最常见的坑。"

### 追问预案

| 追问 | 答 |
|---|---|
| cron 五段格式 | 分 时 日 月 周；`0 2 * * *` = 每天 02:00；`*/5` 每 5 分钟 |
| 为什么脚本用绝对路径 | cron 的 PATH 只有 /usr/bin:/bin，HOME 也不同；不写绝对路径可能找不到命令或写错位置 |
| cron 任务失败怎么发现 | 输出重定向到日志定期检查；或加失败告警；生产用 systemd timer 支持失败通知和补跑 |
| 服务器重启后 cron 任务还在吗 | 在，crontab 持久保存在 /var/spool/cron/，cron 服务设了开机自启 |
| 临时禁用一个任务 | crontab -e 在行首加 `#` 注释掉，或 `sudo systemctl stop cron`（全局停，慎用） |
